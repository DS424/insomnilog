# ADR 0013: Sinks compose a shared `StreamSink` engine and delegate to it

- Status: Accepted
- Date: 2026-08-25

## Context and Problem Statement

Every streaming sink does the same thing per record: take a lock, clear a
reusable scratch `String`, format the record into it, and write it plus a
newline to a writer. Only the *destination* differs — stdout, an append-mode
file, a fresh file per session, later a rotating file.

The original `ConsoleSink<F, W: Write>` was already writer-generic; the only
console-specific code in it was the constructor that built
`BufWriter::new(io::stdout())`. Adding file sinks therefore raised a
structural question rather than an implementation one: how do several public
sink types share one write loop, in a language with no trait-impl
inheritance?

## Considered Options

- **Type aliases over one generic engine**
  (`type ContinuousFileSink<F> = StreamSink<F, BufWriter<File>>`), with the
  differences living only in inherent constructors. Zero boilerplate and a
  single `Sink` impl — but `ContinuousFileSink` and `SessionFileSink` become
  the *same* type, distinguishable only by which constructor was called. No
  room for per-sink documentation, no room for either to diverge later.
- **Duplicate the write loop into each sink.** Rejected: copies the
  lock/scratch/newline logic per sink, with drift risk on every change to
  line shape or locking.
- **`Deref` to the engine.** Rejected: `Deref` forwards *inherent* calls
  only; it does not make a wrapper satisfy `dyn Sink`, and the backend stores
  `Arc<dyn Sink>`. It would save nothing here.
- **A blanket `impl<T: HasEngine> Sink for T`.** Rejected: it would *force*
  every sink to delegate `write_record` identically — precisely the freedom a
  rotating sink needs (see ADR 0014).
- **Composition plus delegation (chosen).** Each public sink is its own
  struct holding an `engine: StreamSink<F, W>` field and forwarding the three
  `Sink` methods to it.

## Decision Outcome

Chosen: **one generic `StreamSink<F, W: Write>` engine; each public sink is a
distinct struct that holds one and delegates `write_record` / `flush` /
`level` to it.**

- `StreamSink` owns the write loop and the `Mutex<(writer, scratch)>`. The
  lock deliberately spans format *and* write so concurrent sinks cannot
  interleave bytes mid-line.
- `ConsoleSink`, `ContinuousFileSink`, and `SessionFileSink` are nominal
  types wrapping a preconfigured engine. Each gets its own constructor
  signature, its own doc page, and room to diverge.
- The three forwarders are generated by a small internal
  `delegate_sink_to_engine!` macro rather than hand-written per sink, so
  there is one delegation code path to read and to test.
- **`StreamSink` is public, not crate-internal.** It is the general-purpose
  "stream to any `io::Write`" sink — an in-memory `Vec<u8>` in tests, a pipe,
  a socket — so users are not forced to reimplement `Sink` for destinations
  the named sinks do not cover. It also replaced `ConsoleSink`'s former
  custom-writer constructor, which was a breaking change to that API.

### Consequences

- Adding a streaming sink means writing a constructor plus one macro
  invocation; the write loop itself is never touched.
- Sink types are not interchangeable at the type level even where their
  runtime behavior is identical (`ContinuousFileSink` vs `SessionFileSink`).
  That is intended — the difference is in construction semantics, and the
  type is where users read about it.
- Tests drive `StreamSink` directly with a `Vec<u8>` writer to assert output
  bytes, and drive the wrappers to keep the delegation covered.
- A sink that must act *inside* `write_record` does not use this engine at
  all; see ADR 0014.
